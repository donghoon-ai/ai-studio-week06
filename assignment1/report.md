# 프롬프트 3기법 비교 리포트

 

## 1. 과업 정의

- 선택: (가) 문의 분류

- 분류 항목과 긴급도 기준: 

  분류 항목 : [주문/배송/환불/제품문의/기타] 
  
  긴급도 기준 :  1) 시간 민감성 2) 금전적/시스템 오류 3) 고객의 감정 및 클레임 가능성 4) 문의의 목적

  긴급도 3 : 바로 개입하지 않으면 금전적 피해, 배송 사고, 심각한 고객 불만이 발생하는 문의

  긴급도 2: 위급한 상황은 아니지만, 직원의 조치나 확인이 필요한 문의

  긴급도 1: 시간제약이 없는 단순 정보 조회나 규정 확인 문의  

- 출력 형식: {"type": ..., "urgency": ...}

## 3. 프롬프트 전문

### Zero-shot
```
리뷰 : "{리뷰 내용}"

위 리뷰를 보고 분류 항목(type)과 긴급도(urgency)를 판단해 주세요.
- 분류 항목: [주문, 배송, 환불, 제품문의, 기타] 중 하나로 분류하세요.
- 긴급도: 1에서 3까지의 숫자로 분류하며, 3이 가장 높은 긴급도입니다. 긴급도는 1) 시간 민감성, 2) 금전적/시스템 오류, 3) 고객의 감정 및 클레임 가능성, 4) 문의의 목적, 이 4가지 기준을 종합하여 판단하세요.

출력 양식은 JSON이며, 불필요한 설명 없이 가장 마지막 줄에 {"type": "분류", "urgency": 숫자} 형식의 JSON 데이터만 딱 한 줄로 출력해 주세요.
```

### Few-shot
```
다음 형식과 예시를 참고하여 마지막에 주어진 리뷰를 분류하세요.
분류 항목은 [주문, 배송, 환불, 제품문의, 기타] 중 하나이며, 긴급도는 1~3(3이 가장 높음)으로 분류합니다.


(예시)
리뷰 : "상품이 파손돼서 왔어요. 당장 환불해 주세요, 급합니다!"
출력 : {"type": "환불", "urgency": 3}

리뷰 : "주문한 색이랑 다른 게 왔는데 교환 말고 환불도 되나요?"
출력 : {"type": "환불", "urgency": 2}

리뷰 : "이거 원래 이렇게 소리가 나는 게 정상인가요? 불량이면 바꿔주세요."
출력 : {"type": "제품문의", "urgency": 2}

출력 양식에 맞춰 불필요한 설명 없이 가장 마지막 줄에 {"type": "분류", "urgency": 숫자} 형식의 JSON 데이터만 딱 한 줄로 출력해 주세요.

리뷰 : "{리뷰 내용}"
출력 :
```
### CoT
```
다음 리뷰를 읽고 분류 항목과 긴급도를 판단하세요.
리뷰 : "{리뷰 내용}"

아래의 1~6단계에 따라 추론하고 가장 마지막 줄에 결론을 JSON 형식으로 작성해 주세요.

1단계 : 리뷰의 내용을 분석하여 [주문, 배송, 환불, 제품문의, 기타] 중 어떤 카테고리에 가장 적합한지 type을 추론한다.
2단계 : 해당 리뷰의 시간 민감성(즉시 처리해야 하는지 여부)에 대해 판단한다.
3단계 : 금전적 피해나 시스템 오류가 발생한 상황인지 판단한다.
4단계 : 고객의 현재 감정 상태 및 강력한 클레임으로 이어질 가능성을 판단한다.
5단계 : 단순 정보 확인인지, 즉각적인 조치가 필요한 문의인지 목적을 판단한다.
6단계 : 2~5단계의 분석을 종합하여 긴급도를 1~3 중에 하나로 최종 결정한다. (3이 가장 긴급함)

결론 : {"type": "분류", "urgency": 숫자} 양식만 작성할 것
 ```

## 6. 분석

- **형식 준수**: Zero-shot, Few-shot, CoT 모두 사전에 지시한 JSON 형태의 출력 형식을 준수했다. 가장 마지막 줄에 JSON 데이터만 한 줄로 출력해달라고 입력하여 가장 마지막 줄에 따로 JSON만 출력하였다. CoT기법의 경우 추론 과정에 관한 설명과 별개로 가장 마지막 줄에 따로 JOSN 형식만 출력해주어 따로 인덱싱해갈 수도 있었다. 

- **분류 정확성**: 명확한 문의에 대해서는 CoT기법이 가장 분류를 잘 수행하였다. 하지만 의도가 애매한 사례에서는 세 기법 모두 정답을 도출하지 못했다.

  Zero-shot (정답률 2/5): 사전 지식 없이 기준만 주어지다 보니, 단순 정보 조회인 #1번 사례의 긴급도를 2로 과대평가했다. 또한 복합적인 문맥(#4, #5)을 정확히 파악하지 못하고 오답을 냈다.

  Few-shot (정답률 2/5): #3번 사례에서 고객의 문장 속 '주문'이라는 단어에 매몰되어 실제 의도인 '배송'을 놓치는 한계를 보였다. 다만, 예시로 주어진 상황과 유사할 경우에는 지시된 기준을 잘 따르는 편이다.

  CoT (정답률 3/5): 6단계의 추론 과정을 거치며 시간 민감성, 금전적 피해 여부 등을 차분히 분석한 덕분에 명확한 사례(#1, #2, #3)를 모두 완벽하게 분류했다.

  애매한 문의들에서 LLM들은 최종 요구 사항이나 표면적으로 드러난 강한 단어에 가중치를 두는 경향이 있어, 사람이 설정한 기준과 엇갈리는 결과가 발생했다.

- **일관성**: 애매한 문의를 기법별로 3회씩 반복 테스트한 결과, 모든 기법이 3회 내내 동일한 결과값을 출력하여 높은 일관성을 확인했다. 반면에, Zero-shot기법은 환불이라는 단어에 반응해 긴급도를 최고 단계인 3으로 높게 고정했지만 CoT는 자체 추론 과정을 통해 환불 문의의 맥락을 분석하고 긴급도를 2로 도출하였다. 이를 통해 각 프롬프트 기법이 텍스트를 해석하는 고유의 시각이 고정되어 있음을 보여준다.

- **비용**: 
  Zero-shot & Few-shot: 중간 추론 과정 없이 곧바로 단 한 줄의 JSON 결과만 출력하므로 출력 토큰 수가 매우 적다. 따라서 응답 속도가 빠르고 API 사용 비용이 가장 저렴하다.   

  CoT: 정확도는 가장 높지만, 결론을 내리기 전 1~5단계의 분석 과정을 모두 텍스트로 생성해야 하므로 출력 토큰 소비가 급증한다. 대량의 고객 문의를 실시간으로 자동화 처리해야 하는 비즈니스 환경에서는 비용 상승과 시스템 응답 지연을 초래할 수 있는 단점이 있다.

 

## 7. 결론 — 우리 팀이 쓸 기본 전략
계약 변경 이력, 부정당제재 사유 등의 텍스트를 분석하여 데이터를 만들 때는 CoT기법을 사용한다. 정답 데이터는 신뢰도가 높아야 하므로 가장 정확도가 높은 CoT기법을 사용하고 추론 과정을 확인하여 정확도를 극대화한다.

계약 분류, 기업 매칭 등의 데이터에서 숫자를 추출하는 작업에는 방대한 양의 데이터를 정리해야하므로 Few-shot기법을 사용한다. CoT기법에 비해 비교적 토큰이 적게 드므로 해당 기법을 사용하여 데이터를 추출한다.
